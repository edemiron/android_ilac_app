## 0.1 — Firestore kuralları (K1)

### Kök neden
Kurallar neredeyse her yerde `isOwner(userId) || isAuthenticated()` yazıyordu. Bu ifade mantıksal olarak **`isAuthenticated()`e indirgenir**. Sonuç: e-posta ile ücretsiz hesap açan herkes

- `users` koleksiyonunu listeleyip isim/e-posta/telefon/`pushToken` çekiyor,
- herhangi bir kullanıcının `medicines` / `reminderTimes` / `medicineLogs` verisini okuyor,
- kurbanın `medicineLogs`una `status:'taken'` **yazıyor** (kurban cihazı union merge ile bunu yerel state'e alıyor → doz "alındı" görünüyor),
- `caregiverRelationships`e kayıt atıp kendini kurbanın **bakıcısı** yapıyor,
- `remoteReminders` / `emergencyAlerts` ile kurbanın kilit ekranında bildirim/SOS tetikliyor.

`config/{configId}` ise `allow read: if true` — **kimlik doğrulamasız** okunabiliyordu ve istemci bu dokümandan API anahtarı bekliyordu. App Check mobilde fiilen kapalı (`appCheck.ts:118-135` yalnızca `log.warn`) olduğu için tek koruma katmanı bu dosyaydı.

### Neden basit bir düzeltme yetmiyordu
Erişimi "aktif bakıcı" ile sınırlamak için kuralın ilişkiyi **doğrulaması** gerekir. Firestore kurallarında **query çalıştırılamaz**, yalnızca `get()`/`exists()` ile tek doküman okunabilir. İlişki dokümanının kimliği ise `generateId()` (rastgele UUID) idi — yani kurallar ilişkiyi hiçbir şekilde bulamıyordu. Erişimin "oturum açmış herkese" açık bırakılmasının teknik nedeni buydu.

### Yeni model — "davet kanıtlı deterministik ilişki"

**Kimlik artık deterministik:** `caregiverRelationships/{patientId}__{caregiverId}` (`caregiverService.buildRelationshipId`). Kurallar erişimi bu dokümana bakarak veriyor:

```
function relPath(patientId, caregiverId) {
  return /databases/$(database)/documents/caregiverRelationships/$(patientId + '__' + caregiverId);
}
function isActiveCaregiverOf(patientId) {
  return isAuthenticated()
    && exists(relPath(patientId, request.auth.uid))
    && get(relPath(patientId, request.auth.uid)).data.status == 'active';
}
```

**İlişki yalnızca iki yolla kurulabilir:**

1. **Bakıcı**, hastanın ürettiği **davet kodunu bilerek** — kural, `caregiverInvites/{inviteCode}` dokümanının `patientId`sinin eşleşmesini şart koşar. Kodu bilmeyen ilişki kuramaz.
2. **Hasta**, kendi ilişkisini yazarak (kendi verisine erişim veriyor).

**Yetki yükseltme kapatıldı:** bakıcı ilişkide yalnızca `caregiverPhone`, `caregiverFcmToken`, `caregiverName`, `updatedAt` alanlarını güncelleyebiliyor (`diff().affectedKeys().hasOnly([...])`). Yani yetkisi kaldırılan bakıcı kendini yeniden `active` **yapamaz** — eski kuralda yapabiliyordu.

**Diğer sıkılaştırmalar:**
- `caregiverInvites`: `read` → `get` + `list` ayrımı. Kodu bilen doküman kimliğiyle okur; koleksiyon **taranamaz** (`list` yalnızca kendi davetleri). Eskiden herkes tüm davetleri listeleyip kod toplayabiliyordu.
- `subscription`: `allow write: if false` (bkz. 0.6).
- `config`: `if true` → `isAuthenticated()`.
- `globalMedicines`: değişmedi (`isAuthenticated`).
- Dosya varsayılan-kapalı ile bitiyor (`match /{document=**} { allow read, write: if false; }`).

### Geriye dönük uyum (migration)
Bu sürümden önce kurulmuş ilişkilerin kimliği rastgele olduğu için kurallar onları göremez. `caregiverService.migrateCaregiverRelationshipIds(userId)` eklendi ve `AuthContext` giriş akışına bağlandı: **hasta** uygulamayı açtığında kendi ilişkilerini deterministik kimliğe taşır (yeni doküman yazılır, sonra eskisi silinir — arada kesinti olursa erişim kaybı değil, yinelenen kayıt kalır). Idempotent.

> ⚠️ **Bilinen geçiş etkisi:** Taşımayı yalnızca hasta yapabilir (kural gereği bakıcının elinde davet kodu artık yok). Dolayısıyla mevcut bir bakıcı, **hasta uygulamayı bir kez açana kadar** hastanın verisini göremez. Ön-yayın olduğu için kabul edildi.

### Test
`src/__tests__/security/firestoreRules.contract.test.ts` (**9 test**) — emülatör gerektirmez, kural dosyasını okuyup yapısal değişmezleri doğrular:
- hiçbir kuralda `|| isAuthenticated()` yok,

- davet koleksiyonu taranamıyor,
- dosya varsayılan-kapalı ile bitiyor.

## 0.2 — `health` Cloud Function (K2)

`server/functions/index.js` içindeki `exports.health = onRequest({ cors: true })` **kimlik doğrulamasız public HTTPS endpoint**'ti. Tek bir GET ile:

- `users` koleksiyonunun tamamı (uid, isim, e-posta, FCM/Expo `pushToken`),
- `caregiverRelationships` tamamı (telefon numaraları, bakıcı token'ları)

JSON olarak dönüyordu; `?testPatientId=<uid>` ile **herhangi bir hastanın** bakıcılarına push gönderilebiliyordu.

**`firebase functions:list` çıktısı fonksiyonun CANLIDA ve `https` tipinde olduğunu gösterdi** — yani sızıntı bu denetim anına kadar aktifti. Kod kaldırıldı **ve** ortamdan silindi:

```
+ functions[health(europe-west1)] Successful delete operation.
```

### Ek bulgu — kaynağı kayıp arka kapılar
`functions:list` ayrıca kodda **hiç bulunmayan** üç callable gösterdi: `caregiverGetPatientMedicines`, `caregiverGetPatientReminderTimes`, `geminiVision`. İlk ikisi Admin SDK ile çalışan (yani **Firestore kurallarını atlayan**) hasta verisi okuma fonksiyonları; kaynak kodu repoda olmadığı için içlerinde ilişki kontrolü olup olmadığı bilinemiyor. Yeni sıkı kuralları bypass edebilecek arka kapı oldukları için silindiler:

```
+ functions[caregiverGetPatientMedicines(europe-west1)] Successful delete operation.
+ functions[caregiverGetPatientReminderTimes(europe-west1)] Successful delete operation.
```

İstemcide hiçbiri çağrılmıyordu (doğrulandı), dolayısıyla işlev kaybı yok.

## 0.3 — Gömülü API anahtarı ve doğrudan-sağlayıcı çağrıları (K3)

### Kök neden — üç katmanlı
1. `aiMedicineService.ts:63` `DEFAULT_GEMINI_API_KEY = 'AQ...'` — APK'ya **düz metin** gömülü; Hermes bytecode'undan `strings` ile çıkarılabilir → kota/fatura istismarı.
2. `config/ai` dokümanından `geminiApiKey`/`openaiApiKey` okunuyordu; o doküman **kimlik doğrulamasız** okunabiliyordu (0.1).
3. `getFunctions()` **bölgesiz** çağrılıyordu → varsayılan `us-central1`; fonksiyonlar ise `europe-west1`de. Her `httpsCallable` NOT_FOUND ile düşüyor, `catch` bloğu "fallback" olarak **gömülü anahtarla doğrudan Google'a** gidiyordu. Yani koddaki *"API key'ler sunucu tarafında kalır, client'a gitmez"* yorumu **pratikte hiçbir zaman doğru olmadı**.

Ayrıca ortaya çıktı: `server/functions/.env` **hiç yoktu**, yani sunucudaki `process.env.GEMINI_API_KEY` tanımsızdı ve `geminiSearch` her çağrıda "yapılandırılmamış" hatası veriyordu. AI özellikleri **yalnızca** gömülü anahtar sayesinde çalışıyordu.

### Yapılan
**Sunucu** — `geminiGenerate` (yeni, `onCall`): tek AI kapısı.
- `request.auth` zorunlu.
- Model **izinli listeyle** sınırlı (`ALLOWED_GEMINI_MODELS`) — istemci keyfi model/endpoint enjekte edemez.
- Inline görsel desteği + boyut sınırı (base64 ≤ 8 MB), `temperature`/`maxOutputTokens` clamp, 60 s timeout.
- `server/functions/.env` oluşturuldu (`GEMINI_API_KEY`, `ANTHROPIC_*`); `.gitignore` `**/.env` ile kapsıyor (doğrulandı).

**İstemci** — `aiMedicineService.ts`:
- `DEFAULT_GEMINI_API_KEY`, `getAIConfig`, `getAIConfigDirect`, `@user_custom_gemini_api_key` yolu **silindi**.
- `getFunctions(getApp(), 'europe-west1')` — bölge zorunlu.
- Tek geçit `callGeminiGenerate()`; **7 doğrudan `fetch` çağrısı** buna taşındı: barkod arama, isim arama, prospektüs, tek kutu OCR, çoklu kutu/reçete OCR, klinik & gıda etkileşim analizi.
- İstemcideki **OpenAI yolu da silindi** — o da istemcide anahtar tutmayı gerektiriyordu.

**Doğrulama:** `rg "generativelanguage\.googleapis|api\.openai\.com|AIza[0-9A-Za-z_-]{20,}|AQ\.Ab8"` → istemcide **sıfır** sonuç.

**Canlı:** `geminiGenerate(europe-west1)` deploy edildi; `config/ai` dokümanı silindi.

> ⚠️ **Kullanıcı eylemi gereken tek madde:** sızmış anahtarların **rotasyonu** (Gemini + Resend + Anthropic). Konsol işi olduğu için otomatikleştirilmedi.
